# 内部协作材料（不随本仓库发布）

本仓库是 TokenLedger 的**公开发布版**。它包含产品代码、跨端契约、需求与设计事实、构建与发布脚本，以及面向外部贡献者的协作说明。

项目在内部开发时使用了一套更完整的协作材料：**任务台账、逐任务派单简报、结构化证据日志、内部评审与审计报告**。这些材料记录了每个任务的实现过程、验证证据与决策流水，对内部审计有价值，但**不随公开仓库发布**。

## 不发布的材料

| 目录 / 文件 | 内容 | 为什么不发布 |
|---|---|---|
| `docs/TASKS.md`、`docs/TASKS-archive.md` | 任务台账：未闭合任务、已归档行、活跃认领 | 内部工单与迭代节奏，不属于产品事实 |
| `docs/task-logs/` | 每个任务的派单简报与结构化证据日志 | 含本机绝对路径、机器标识与内部审阅流水 |
| `docs/audits/` | 内部评审与审计报告 | 含未脱敏的内部过程记录 |
| `docs/plans/` | 内部迭代计划 | 同上 |
| `docs/archive/` | 已结束的迭代材料、TEAM-v1 协作材料、旧评审 | 历史过程材料，非当前事实源 |
| `docs/runbooks/` | 内部运维流程 | 依赖内部台账与审批链 |
| `docs/BACKLOG.md` | 轮末待办清单 | 内部工单条目 |
| `CLAUDE.md` | 内部智能体入口指针 | 内部工具链入口 |
| `skills-lock.json` | 内部智能体技能锁文件 | 与产品无关 |

公开仓库里**仍然保留**的文档是产品事实源：`docs/PROJECT.md`（公共事实、平台边界、架构决策）、`docs/REQUIREMENTS.md`（需求与验收标准）、`docs/DESIGN.md`（技术设计）、`docs/contracts/**`（跨端机器契约）、`docs/design/**`（专题设计稿）、`docs/integrations/**`（外部能力来源与边界）。

## 设计文档里为什么会引用这些路径

`docs/design/**` 与 `docs/DESIGN.md` 里仍能看到 `docs/task-logs/...`、`docs/BACKLOG.md` 这类路径。它们是**内部溯源标记**——记录某条设计结论是在哪次任务里定的。

- 这些引用**不是可点击的相对链接**，不会渲染成 404 的超链接。
- 它们指向的实体不在本仓库，因此**无法公开查阅**。这不是遗漏，是发布范围的取舍。
- 公开版的读者应把这些引用理解为「该结论有内部出处」，而不是「去这里看」。

如果你在公开仓库里找不到某个设计结论的完整决策上下文，那是预期的：完整过程材料在维护方的私有仓库中。

## 状态与台账的公开替代

内部台账的状态枚举（`[ ]` `[~]` `[r]` `[v]` `[x]` `[!]` `[?]`）与两条状态轴（`integration` / `validation`）在 `docs/PROJECT.md` §3.2 有完整定义，本仓库保留该定义。公开仓库没有任务行，因此 `npm run check:docs` 只校验与台账无关的契约部分——这是有意为之，不是门禁失效。

## 反馈

功能问题、缺陷与改进建议请走 [Issues](https://github.com/Geidorf/TokenLedger-open/issues)。若某条设计结论看起来自相矛盾，欢迎开 issue 指出来——内部材料不在公开仓库，公开讨论是让结论收敛的主要途径。
