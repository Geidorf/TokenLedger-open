## 0. 结论

1. **主标签只有一个：预估费用。** 旁注固定为「按价格表估算，非账单」。预估成本、估算成本、预估总成本、预计成本、花费成本、花费金额、成本、金额（作标签时）一律改成「预估费用」或其短形「费用」。
2. **登记订阅后，预估费用拆成三份**：订阅覆盖的叫「API 等值」，按量付费工具的叫「预估支出」，尚未设置付费方式的叫「其余」。三者相加等于预估费用；每条记录只归一类。
3. **回本倍数只按计费周期算**：一个计费周期内该订阅覆盖记录的 API 等值 ÷ 该周期订阅费。看板上的金额跟随所选范围，回本倍数不跟随，出现时必须写明计费周期。
4. **没登记订阅时**，各处数字与今天完全相同，只是换成新叫法并加旁注。
5. **订阅设置首期只存本机**，不上传；Android 首期只统一叫法，不显示拆分与回本。跨设备同步列为可选的第三期。
6. **实施分三期**：A 统一叫法与未知值（桌面、托盘、Android），B 桌面本机订阅与回本，C 跨设备与 Android 回本（可选）。A 在 T10.150 合入后立即开始。

## 2. 口径与公式

### 2.1 记录级费用

每条账本记录 r 的费用 `cost(r)`（美元）：

- 扫描器从工具日志拿到费用时直接采用：MiniMax（v2 runtime）、OpenCode、Kilo、ReasoniX、Hermes、WorkBuddy、Qclaw（以 `src-tauri/src/commands/mod.rs` `mark_scanner_costs_for_repricing` 的注释与排除列表为准）。账本没有记录费用来源的列（同一注释指向评审 #09 的 `cost_source`），界面无法逐条区分「估算」与「来源上报」，因此统一称「预估费用」，帮助说明写明两种来源。
- 其余按价格表估算（`src-tauri/src/commands/mod.rs` `estimate_cost`）：输入 × 输入价 + 输出 × 输出价 + 缓存读 × 缓存读价 + 缓存写 × 缓存写价，单价为每百万 Token 美元价；缺缓存读价按输入价 × 0.1，缺缓存写价按输入价 × 1.25；没有匹配的模型按工具兜底价（设置页显示为「待核价」），再退到 `default`。
- 价格表全部是美元（`MODEL_PRICING.md`）。人民币标价的模型由维护者按约 7.2 CNY/USD 折算后写入；Android 显示人民币同样默认用 7.2（`apps/android/app/build.gradle.kts` 的 `TOKENLEDGER_CNY_EXCHANGE_RATE`）。
- 本机统计里每条记录总有一个有限数值。云端 Stats v2 RPC 的必填汇总（`summary.totalCost`、`tools[].cost`）用 `sum(coalesce(cost_usd, 0))` 把空费用按 0 相加，只有可选的 `models[].cost` 和 `dailyCosts` 会在费用不全时缺失。这是既有局限，本方案不改，只在说明里如实写出。

### 2.2 预估费用

`预估费用(S) = Σ_{r ∈ S} cost(r)`，S 是看板当前的规范化查询（范围、时区、设备、工具、模型、搜索），即 `summary.totalCost`。

### 2.3 付费方式归类

每条记录按以下顺序归入且只归入一类：

1. **订阅覆盖**：存在订阅 p，满足
   - `r.tool ∈ p.tools`；
   - `p.modelPrefixes` 为空，或 `r.model` 以其中某个前缀开头（ASCII 不区分大小写）；
   - `p.machines` 为空，或 `r.machine_id ∈ p.machines`；
   - `p.startDate ≤ r 的本地日期 ≤ p.endDate`（`endDate` 为空表示仍在订阅）。
2. **按量付费**：不被任何订阅覆盖，且设置里把 `r.tool` 标为按量付费。
3. **其余**：以上都不是。

两个订阅在同一时段覆盖同一条记录时无法判断记录来自哪个账户，因此保存时直接拒绝（§3.2），不做平分或重复计入。同一工具可以在不同时段属于不同订阅（换方案），也可以按模型前缀同时属于不同订阅（例如 Claude Code 里 `claude-*` 属于 Claude 订阅、`glm-*` 属于另一个编程套餐）。

### 2.4 API 等值、预估支出与其余

- `API 等值(S) = Σ_{r ∈ S，订阅覆盖} cost(r)`；按订阅拆开为 `API 等值_p(S)`。
- `预估支出(S) = Σ_{r ∈ S，按量付费} cost(r)`。
- `其余(S) = Σ_{r ∈ S，其余} cost(r)`。
- 恒等式：预估费用 = API 等值 + 预估支出 + 其余（三者都可得时）。
- 一个订阅覆盖多个工具时，其 API 等值是这些工具被覆盖记录之和。

### 2.5 回本倍数（只按计费周期）

**计费周期。** 月付：计费日为 a 时，每月的计费日期取 `min(a, 当月天数)`（计费日 31 在 2 月按 28/29 日）；周期为 [本次计费日, 下次计费日)，按本地日期划分，时区与看板查询一致。年付：以开始日期的月日为计费日，2 月 29 日在平年按 2 月 28 日。

**周期订阅费。**
- 整个周期都在订阅有效期内：`F_c = 订阅费`，不折算。进行中的周期同样用全额，因为订阅费是周期开始时付清的。
- 订阅在周期中途开始或结束（首个或最后一个周期、换方案）：`F_c = 订阅费 × 有效天数 ÷ 周期天数`，按日历天计算，避开夏令时；界面写明「按 25/30 天折算」。这是对供应商升降级折算的近似，实际以账单为准。
- 人民币订阅费按换算汇率折成美元：`F_c(USD) = F_c(CNY) ÷ 汇率`。

**回本倍数。** `回本倍数_c(p) = API 等值_p(W_c) ÷ F_c(USD)`，其中 `W_c = [max(周期起点, 开始日期), min(周期终点, 结束日期 + 1 天, 现在))`。

- 进行中的周期显示「截至今天」的值，并写明「已过 10/30 天」。它会随周期推进增大，不做外推。按当前节奏推算周期末倍数属于 D2 预测，只能按 T10.153 的规则单独标「预测」。
- 已结束的周期是最终值，可在订阅卡「历史周期」里查看。
- 只陈述数字与公式，不写「值」「不值」「划算」等评价。
- 显示：`0 < y < 0.1` 写 `<0.1`；`0.1 ≤ y < 10` 保留一位小数；`y ≥ 10` 取整；没有用量写「0 倍」；分子或分母不可得写「—」并给原因。

### 2.6 每个数字指的是哪一段时间

| 数字 | 时间段 | 是否跟随看板筛选 | 作用域 |
|---|---|---|---|
| 预估费用 | 所选范围（同一规范化查询） | 跟随 | 本机或云端，与看板一致 |
| API 等值 / 预估支出 / 其余（看板、排行、专属看板） | 所选范围 ∩ 订阅有效期 | 跟随 | 同上 |
| API 等值（订阅回本卡、设置页） | 该订阅的计费周期；进行中为周期起点至今 | 不跟随，只按订阅自身的工具、模型前缀、设备 | 同上 |
| 回本倍数 | 同上 | 不跟随 | 同上 |
| 周期订阅费 | 计费周期；部分周期按天折算 | — | — |
| 缓存节省、单位费用、费用占比 | 所选范围 | 跟随 | 同上 |

**为什么回本不跟随所选范围。** 让「今日」「本周」也算回本，只有两种做法：一是把进行中窗口的订阅费按已过时间均摊，这等于按当前节奏外推到周期末，属于 D2 预测；二是用整期订阅费当分母，「今日回本 0.03 倍」没有意义。两种做法还会让同一个「回本」在看板和订阅卡上出现两个数。因此看板上的金额跟随范围，回本倍数一律属于计费周期，出现时写明「本计费周期」。

看板显示哪一个周期：取包含所选范围截止时刻的那个周期（截止时刻优先 `comparison.window.currentEnd`，其次 `meta.generatedAt`）。所选范围在过去时，显示当时那个已结束周期的最终值；截止时刻不在某个订阅的有效期内时，看板不显示该订阅的回本。

### 2.7 币种与换算

- 账本、价格表与所有预估费用都以美元计。订阅费可以是美元或人民币（首期只支持这两种）。
- 换算汇率默认 7.2，与价格表人民币标价的折算惯例及 Android 的默认值一致；用户可在设置中改为 1–20 之间、最多 4 位小数的值。不联网获取实时汇率：实时汇率会让没有新用量的数字每天自己变化，也要多一次联网。
- 汇率保持 7.2 时，人民币订阅覆盖的若都是人民币标价模型，分子分母用的是同一汇率，回本倍数等于直接按人民币计算的结果。改动汇率只影响订阅费一侧，价格表里已写入的美元单价不变，所以这种情况下改汇率反而会让倍数偏离人民币直算结果。设置页须说明这一点。
- 凡是经过换算的数字都要注明汇率，例如「¥199/月（≈$27.64，按 1 美元 = 7.2 元）」。先按全精度计算，只在显示时舍入。
- 桌面金额一律显示美元。Android 默认显示人民币（点按可切换美元）。第三期同步订阅设置后，Android 计算回本和把 API 等值换成人民币时必须用订阅设置里的汇率，确保两端倍数一致。

### 2.8 未知与不可得

- 任一参与计算的金额缺失、非有限或为负时，对应的 API 等值、预估支出、其余与回本倍数显示「不可得」。不拿已知部分冒充总额，不显示 $0.00；真实 0 仍显示 ≈$0.00。
- 某一份不可得时，其他可得的份照常显示，恒等式不再展示。
- 覆盖记录中含「待核价」模型时（桌面本机可从价格表 `_meta.status = auto_discovered` 判断），回本倍数照常显示，说明里写「其中 ≈$x 来自待核价模型，按工具兜底价暂估」，并给出去设置核价的入口。
- 现有格式化函数把非有限值画成 `$0.00`（`src/utils/format.ts:20-27`、Android `CurrencyUnit.convertFromUsd` 与 `formatCny`、托盘 `summary_numbers` 的 `unwrap_or(0.0)`），A 期一并改为「不可得」（§5 各行「未知值处理」列）。

### 2.9 本机与云端作用域

- **本机**：只含这台电脑的记录。一个订阅在多台电脑上使用时，本机回本倍数偏低；订阅卡写「仅本机记录，其他设备上的使用未计入」。
- **云端（全部设备）**：含所有已同步设备，受订阅自身的设备范围约束，不受看板设备筛选约束。本机还有待上传记录时沿用现有「云端可能不完整」提示。
- **桌面云端的限制**：C0（T10.185）已开放桌面云端自定义日期，生产迁移已于 2026-09-25 确认（U-10），按计费周期查询可直接用 custom 范围（`dashboard-stats-v2.md` §4）。C0 之前的替代（已不需要，留作旧云端的降级参考）：计费日为 1 的月付订阅，进行中周期等于「本月」预设，可以直接算；其他情况显示「云端暂不支持按计费周期统计；可切到本机查看本机部分」。看板的范围拆分在订阅覆盖整个所选范围、且没有模型前缀和设备范围时，可直接用 `tools[].cost` 算出，云端同样适用；其余情况云端显示「不可得」。
- Android 在第三期前不显示拆分与回本（§3.5）。

### 2.10 已知局限（写进帮助说明）

1. 同一工具既用订阅登录又用 API key 时，日志无法区分；订阅有效期内该工具的记录都算 API 等值。可用模型前缀或设备范围部分区分。
2. 订阅额度用完后改走额外用量或 Credits 计费的部分实际另付费，账本无法识别，仍计入 API 等值。
3. 工具日志自带费用时，若工具在订阅登录下把费用记为 0，API 等值会偏低（需在 B 期核实 OpenCode、Kilo 的实际行为）。
4. 价格表是标准单档：长上下文加价、Batch、Priority、渠道加价都未计入（`MODEL_PRICING.md`）。
5. Antigravity、Trae 的 Token 本身是估算（`ESTIMATED_TOOLS`），其费用也是估算之上的估算。
6. 账本没有覆盖的时段（安装前、清理过的旧记录）不计入分子，回本倍数是按账本记录计算的下限。

## 3. 订阅设置模型

### 3.1 字段

订阅方案 `CostSubscriptionPlan`：

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 本机生成的稳定 ID，如 `sub-` 加 16 位十六进制；不随名称或顺序变化 |
| `name` | string | 用户命名，如「Claude Max」 |

### 3.3 存储

- 新增 `AppSettings` 字段 `cost_subscription_plans`、`cost_tool_billing_modes`、`cost_cny_per_usd`、`cost_profile_revision`（`src-tauri/src/settings.rs`，TypeScript `src/types.ts` 同名蛇形字段）。保存在应用数据目录的 `app_settings.json`，所有窗口与 Rust 托盘读同一份。
- 与 `quota_custom_endpoints` 相同，这组字段**不经**通用 `save_settings` 写入，改由专用命令 `get_cost_profile`、`save_cost_profile(profile, expectedRevision)`、`validate_cost_profile(profile)` 读写；保存成功后发出既有 `settings-updated`。这样陈旧的设置页状态不会覆盖订阅设置。
- 读取时 `sanitized()` 丢弃非法条目并记录条数（不记内容），未知 provider、cycle、currency 按条目非法处理，不静默改写成默认值。
- 隐私：订阅名称、费用与覆盖工具属于个人消费信息，但不是凭据，不进系统安全存储；不写日志（只记条数）、不进 CSV 导出、不进云同步；分享海报与简报中的订阅费、API 等值与回本倍数受「隐藏费用」约束。设置页提供「删除全部订阅设置」。

### 3.4 跨设备方案

| 方案 | 做法 | 优点 | 代价与风险 |
|---|---|---|---|
| ① 仅本机（**推荐首期**） | 只存 `app_settings.json` | 零迁移、零上传、实现最小 | Android 与其他电脑看不到拆分与回本 |
| ② 同步订阅设置（推荐作为第三期选项） | 新表按用户保存一份设置 JSON（RLS 只允许本人读写、按 revision 条件更新、删除写墓碑），桌面开关「同步订阅设置到我的设备」默认关闭；Android 读取后用自己的 Stats v2 查询计算 | 各端各自计算，数字口径一致；不上传计算结果 | 需迁移、RLS、契约与测试；订阅费等消费信息会存到当前连接的 Supabase 项目（正式版通常是发布方运营的生产项目），必须显式开启并可删除 |
| ③ 只同步计算结果 | 桌面把每个计费周期的 API 等值与倍数上传 | Android 实现简单 | 结果依赖桌面在线且会过期；与看板查询不同源，不推荐 |
| ④ 复用额度同步通道 | 把订阅包装成额度 Provider | 不需新表 | 语义错位：Quota v1 §1 规定额度与 Token 消耗是两条事实链、不得合并；`manual-budget` 是手工预算额度，不是订阅费（预算按 D3 暂不做）。不推荐 |
| ⑤ Android 另行手填 | 两端各录一份 | 不上传 | 两份配置必然漂移，不推荐 |

### 3.5 Android 呈现对等

### 3.6 未登记任何订阅时

B2 为什么推荐新的本机命令，而不是在前端用现有 `get_cached_stats` 拼：

- 拼接需要按「订阅 × 工具 × 时间窗」多次查询，每次返回完整看板数据；模型前缀只能从 `models[]` 反推，又拿不到工具 × 模型的费用矩阵。
- Rust 逐行归类一次完成，前缀、设备与日期边界都精确；还能识别待核价模型的金额，这一点只有持有价格表的 Rust 能做。
- 归类规则只在 Rust 实现一份，前端与托盘只负责展示，与本机行为分析（T10.149）的做法一致。
- 前端拼接留作云端的快速路径，以及 B2 性能不达标时的退路。

- 未登记订阅时，所有表面的数值与改前逐一相同，只有叫法与旁注变化；GLB-01 场景（缺费用、非有限、负数）显示「不可得」而不是 0。
