# 网关记录上云：magpie 调研与方案（T10.273，U-96）

> **实施状态（2026-10-17 按代码核对）**：已实现（`gateway_cloud.rs`、迁移 `20261004120000_gateway_aggregate_provenance`）。

本文记录 T10.273 的调研结论与据此选定的方案。契约以 `docs/contracts/dashboard-stats-v2.md` §2.5 为准，本文只解释依据。

## 1. 设计前提

本节只记录 TokenLedger 自己的设计依据。早期调研中对第三方实现的字段级分析与实现级复刻属于内部材料，保留在私有仓库，不随本仓库公开。

**去重要解决什么问题。** 同一个请求可能同时出现在两处：Agent 自己的会话日志里（由扫描器读到），以及本机模型网关的请求账本里（网关知道自己转发过什么）。两处都记账会让同一笔用量被统计两次。合并必须在**本机**完成，因为只有本机同时持有这两份数据。

**去重窗口的由来。** 网关的 `ts` 是记账时刻（流结束），`latencyMs` 是整段耗时，因此一条网关记录覆盖区间 `[ts − latencyMs, ts]`。本机存储时间截断到秒，区间两端与扫描时间各可能丢掉不到 1 秒。为了覆盖两侧截断并留出余量，`W` 从早期无依据的 120 秒收紧为 **5 秒**（1 秒 + 1 秒 + 1 秒 + 2 秒余量），并且改为对**整个区间**比较而不是比较时间点：规则 A 的跨度是 `[最早开始 − W, 最晚结束 + W]`，规则 B 的候选要落在 `[开始 − W, 结束 + W]` 内，距离按到区间的最近距离计。按区间比较，就不用依赖 Agent 日志的时间戳写在流开始还是流结束。

**请求 ID 精确匹配暂不可用。** 网关的 `requestId` 是本地随机 ID，不是上游请求 ID；扫描侧只有部分工具的日志带消息/请求 ID。等网关记下上游请求 ID 后，再在规则 A、B 之前加一步精确匹配。

**去重位置：客户端，上传结果。** 云端 `token_logs` 只存「设备 × 工具 × 模型 × 小时」聚合行，没有会话和逐请求数据，RPC 无法在云端去重。因此桌面在本机合并去重，再把合并后的小时聚合上传。云端 RPC 与 Android 不需要再去重，口径自动一致。

**Supabase 能承载。**

| 方案 | 行数量级（每用户每年） | 结论 |
|---|---|---|
| 逐请求上传网关记录（新表） | 重度用户每天约 5 千请求，约 180 万行；每行连索引约 300～500 字节，约 0.5～0.9 GB | 超出免费档 500 MB；RPC 需改为扫描逐请求表；还要上传会话 ID（需哈希）。不采用 |
| 合并后的小时聚合写入现有 `token_logs` | 与现状同量级：每小时每设备最多「工具数 × 模型数」行，网关只增加少量新的（工具，模型）组合 | 采用 |

RLS 沿用 `token_logs` 已有的按 `auth.uid() = user_id` 隔离的四条策略；所有 v1/v2 RPC 都对聚合行求和，不需要改 RPC。只需一条小迁移：

- 新增可空列 `gateway_requests`：该聚合行里来自网关的请求数，仅作来源审计；`null` 表示旧客户端上传（未知）。约束 `0 ≤ gateway_requests ≤ requests`。
- 物化视图脏标记触发器补上 `DELETE`：网关取代扫描行后，某个旧（工具，模型，小时）聚合可能整行消失，桌面需要删除云端旧行；原触发器只在插入/更新时标脏，只删不插会让物化视图停在旧值。

**隐私。** 上传的仍是小时聚合：工具、模型、小时、设备 ID 与 Token、请求数、成本，不含会话 ID、供应商 ID、key、本地 token、请求或回复内容，因此不需要哈希会话。

**设备边界。** 每台设备只上传自己的扫描记录与网关记录。扫描行的 `machine_id` 为空时沿用旧版本的本机语义；非空时必须等于当前设备 ID。普通待同步查询、上传前的网关去重候选与整小时收集、发送身份和旧桶修复使用同一边界，外机行不会进入载荷或本机上传回执。外机记录仍保留在本机账本，价格重算、重置同步状态或切换云账号不会让它们取得上传资格；界面的待上传记录数也只统计本机行，总记录数仍包含恢复的外机行。按聚合键删除云端旧行时同时限定当前用户和设备，避免旧状态里残留的外机键触及其他设备的历史；整工具清理也只读取本机待办。

## 3. 增量、幂等与重试

- 本机状态文件 `app_data/gateway/cloud-sync-v1.json` 记录「用户、设备、每个受网关影响的小时 → 上次上传的聚合指纹与键」。受影响的小时 = 网关记录所在小时 ∪ 被取代扫描行所在小时。
- 每次同步：受影响小时里指纹变化的、或有待同步扫描行的，按合并视图重算该小时的全部聚合并 upsert（`on_conflict=user_id,unique_key`）；上次上传过、或扫描口径会产生、但合并后已不存在的键，从云端删除。全部成功后才写状态文件和扫描行的同步标记；中途失败则下次整体重算，upsert 与按键删除都可重复执行。
- 未受网关影响的小时仍走原有扫描口径，行为不变。旧云端缺 `gateway_requests` 列时，去掉该字段重试一次（与 `cache_write_tokens` 的做法相同）。
- 状态文件属于派生缓存：丢失或换用户时只会多传一次，不会少算。

## 4. 已知边界

- 网关账本只保留当前文件与一个轮转文件（各 16 MB）。更早的网关记录轮转掉以后，那些小时不再算作受影响；云端保留最后一次合并上传的值。只有那些小时又出现新的扫描行时，才会按扫描口径重传，届时该小时的网关贡献会从云端消失。
- 有待执行的 Codex 云端清理（`pending_cloud_purges`）时，本轮跳过网关合并，等清理完成后的下一轮再传，避免与清理交错。
- 旧版本桌面与新版本在同一设备交替使用时，旧版本可能把受影响小时按扫描口径重传，新版本的状态文件察觉不到这次覆盖；需要在新版本里重置云端同步状态（全部扫描行重新标为待同步），下一次同步才会重新合并上传。
