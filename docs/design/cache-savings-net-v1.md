## 0. 结论

1. **现在的「节省」是毛值。** 算法是命中缓存的读取量 × (输入价 − 缓存读价)（`src-tauri/src/commands/mod.rs:3094-3107`），没有扣掉缓存写入比输入贵的那部分。
   - 同一份价格表在预估费用里已经按写价收了这笔钱（`mod.rs:3063-3092`），所以两个数字的口径彼此不一致。
2. **推荐方案 (c)：主值叫「缓存净节省」。**
   - 公式：缓存净节省 = 缓存读取节省 − 缓存写入溢价。
   - 读取节省与写入溢价作为明细，出现在帮助弹层（或缓存面板）和 HTML 简报里。
   - KPI 副行与海报只放净值。
3. **契约只增不改，Stats v2 不升版本。**
   - 保留 `summary.cacheSavedUsd`，语义仍是读取节省（毛值），这是它第一次写进契约。
   - 新增可选对象 `summary.cacheSavings` 与能力位 `meta.capabilities.cacheSavings`。
   - 三种展示方案用的是同一份数据，所以生产端可以在用户选定展示方案之前先做。
4. **未知值的处理：**
   - 读写拆分不可证明时：整体不可得，沿用 T10.88 的门槛。
   - 缺写入单价时：沿用预估费用的兜底（输入价 × 1.25），并标注「含兜底单价」。
   - 净值为负时：带符号照实显示。
   - 海报：只在净值为正时上图。
5. **分两期。**
   - A 期改本机与桌面，含桌面对云端的桥接计算；同时修 Android 把未知存成 0 的问题。
   - B 期给云端加上传列并改 RPC，让 Android 与桌面云端读到同一个数。
6. **另报 10 项现存分歧（§1.8）。** 最要紧的一项：云端同期、明细、实体三类摘要的缓存拆分没有 provenance 门槛（D3）。这会影响 T10.156 的 K4 变化计算，以及云端专属看板上的复用率。

需要用户拍板的 7 件事（详见 §5）：

|---|---|---|
| Q1 | 展示方案 | (c)：主值为净节省，明细列出读取节省与写入溢价 |
| Q2 | 净值为负怎么显示 | 带符号显示 ≈−$x，标签不变，附中性说明 |

## 2. 价格与来源现实

### 2.1 价格表覆盖（`src-tauri/prices.json`）

- 共 95 个键，单位是 USD / 百万 Token。
  - 抽查 `claude-sonnet-4-6` 为 3 / 15。
  - `glm-5.1` 的 1.11 / 3.89 / 0.28 恰好是 ¥8 / ¥28 / ¥2 按 7.2 折算的结果。
  - `MODEL_PRICING.md:3` 也声明全表为 USD。

| 类别 | 键数 | 写价 ÷ 输入价 | 读价 ÷ 输入价 |
|---|---|---|---|
| Claude 4.x/5.x 与兜底键 `claude-unknown` | 9 | 1.25（5 分钟写价） | 0.10 |
| GPT-5.6 系列（sol、terra、luna、`gpt-5.6`） | 4 | 1.25 | 0.10 |
| GPT pro（5.5、5.4、5.2） | 3 | 1.00，无溢价 | 1.00，无折扣 |
| 其余模型 | 79 | 缺写价，预估费用按 1.25 兜底 | 其中 47 个同时缺读价，按 0.10 兜底 |

- 工具兜底键里只有 `claude-unknown` 有写价。`codex-agent`、`gemini-3.5-flash-agent`、`minimax-model`、`reasonix-agent`、`deepseek`、`kimi-k2.6`、`grok-4.3`、`gemini-3.5-flash`、`default` 都没有写价。
- 表外型号在扫描时记入本机发现目录，加载价格时各物化成一条「待核价」条目（R9）。此后所有工具都按型号命中这一条（R2），条目单价抄自观察到该型号的工具中字母序最小者的兜底键：
  - 只经 Claude Code 出现的表外 Claude 型号（如 `claude-opus-4-6`、`claude-opus-5`）按 `claude-unknown` 计价，即 Sonnet 档（3 / 0.3 / 3.75）。
  - 只经 OpenCode 或 Kilo 出现的型号抄 `minimax-model`，只经 Pi 出现的抄 `default`。这两个键都没有写价，所以条目写价按输入 × 1.0（D7）。
  - 字母序更靠前的工具后来也用到同一型号时（例如先只经 OpenCode 出现，后来 Claude Code 也用了），条目改抄那个工具的兜底键，单价随之改变（§6）。
- 只有进不了发现目录的名称（占位名如 `unknown`、非型号字符串，`scanner/runner.rs:114-150`）才按调用工具现查兜底键（`mod.rs:2939-2956`），这时兜底单价取决于工具。

## 3. 定义与选项

### 3.1 共同定义（三种展示方案共用）

对当前规范化查询 S（范围、时区、设备、工具、模型、搜索）里每一条缓存拆分可证明的记录 r，令读取量 R = cached − write，写入量 W = write。单价沿用预估费用的解析与兜底（R2、R3）：

```text
读取节省  G = Σ R × max(输入价 − 读价, 0) ÷ 10⁶      （= 现在的 cacheSavedUsd）
写入溢价  P = Σ W × max(写价 − 输入价, 0) ÷ 10⁶
缓存净节省 N = G − P                                  （可为负）
```

- **含义**：N = 「全部缓存量按新鲜输入计价」减去「按缓存读写价计价」。这就是在同一份价格表下，缓存让预估费用少了多少。
- **两个 max 的作用**：在读价高于输入价或写价低于输入价时生效，各分量保守取 0。勘误（2026-09-25，T10.183 评审 P3-3、root 决定 R-25）：内置表并非不会触发，3 个 MiniMax highspeed 型号的写价 0.36 低于输入价 0.58，写入溢价取 0，净节省因此只会偏低；这些单价由后续价格任务核实，届时再定是否把写入折价计入。
- **不影响其他口径**：有效 Token 仍是输入 + 输出；`totalCost`、缓存读写字段都不变；缓存读与缓存写继续分列。
- **门槛**：与 `cacheReadTokens/cacheWriteTokens` 相同，即 T10.88 的「全部缓存行都可证明」。不满足时 G、P、N 一起不可得。
- **兜底计数**：
  - 「列价」指匹配到价格表中该模型的显式条目，且条目里写了对应字段。工具兜底键、`default`、自动发现的「待核价」条目、字段缺省，都算兜底。
  - 生产端分别统计单价来自兜底的读取量与写入量，供界面标注。
  - 用户改过的自动发现项按用户覆盖算作列价；实现时要核对保存后 `_meta` 是否还在。
- **舍入**：
  - 生产端用全精度 double，逐行或逐组相加，不做中间舍入。云端 B 期用 numeric 累加，转 float8 前检查有限上界（同 T10.88 的 `models.cost`）。
  - 只在呈现层舍入。三个数各自舍入，不用舍入后的 G − P 反推 N。三者并列时加注「各项分别四舍五入，合计可能相差 $0.01」。
  - 例：G = 1.236、P = 0.114、N = 1.122，分别显示为 ≈$1.24、≈$0.11、≈$1.12。
- **格式**：沿用 T10.154 §4.1，并补上负值规则。

  | 值 | 桌面 | Android |
  |---|---|---|
  | v ≥ 0.01 | ≈$20.85 | ¥150.12 |
  | 0 < v < 0.01 | <$0.01 | <¥0.01 |
  | v = 0（含 −0） | ≈$0.00 | ¥0.00 |
  | −0.01 < v < 0 | −<$0.01 | −<¥0.01 |
  | v ≤ −0.01 | ≈−$0.21 | −¥1.51 |

  负号用 U+2212。现有 `formatUsdApprox` 不能直接用于负值（W5）。

### 3.3 推荐与理由

推荐 (c)，写入单价缺失时按兜底计算并标注。理由：

1. 预估费用已经按 1.25× 收了这些写入的钱。MODEL_PRICING 明确「不把缺失解释为免费」。节省若不扣这笔钱，同一张 KPI 行上的两个数就基于不同假设。
2. 兜底方向是保守的：它假设溢价存在，所以净节省不会被高估。对没有写入溢价的供应商，净节省会少算 0.25 × 输入价 × 写入量，而且有标注。
3. 净值为负是真实的信号：写入缓存以后几乎没有复用。例如当天的第一个会话，或一次性的子代理调用。隐藏它等于把已知的负数当成未知。
4. 契约用新增字段表达，旧客户端不受影响，也不需要升 Stats v2 的版本（契约 §7 第 1 条）。

## 4. 改动清单

### 4.1 契约（`docs/contracts/dashboard-stats-v2.md`，root 单写）

新增 §2.4「缓存节省（T10.162，可选）」。这是只增不改的扩展，`meta.contractVersion` 仍为 2。

不采用「直接把 `cacheSavedUsd` 改成净值」，原因有两条：

- 这属于统计语义变化。契约 §7 第 1 条规定，这种变化必须升级版本。
- 旧客户端只接受 ≥ 0 的值，碰到负净值会把它当成不可得。另外，云端桥接与 Android 缓存里的旧值会与新值混在一起，无法区分。

```json
"summary": {
  "cachedTokens": 9000000,
  "cacheReadTokens": 8000000,
  "cacheWriteTokens": 1000000,
  "cacheSavedUsd": 21.6,
  "cacheSavings": {
    "readSavedUsd": 21.6,
    "writePremiumUsd": 0.75,
    "netSavedUsd": 20.85,
    "fallbackPricedReadTokens": 0,
    "fallbackPricedWriteTokens": 0,
    "priceBasis": "local-prices"
  }
}
```

- `cacheSavedUsd`：既有字段，语义不变，即读取节省（毛值）；读者不得把它当作净节省。
- `cacheSavings` 的出现条件与 `cacheReadTokens/cacheWriteTokens` 完全相同，缺失即不可得。
  - `netSavedUsd` 可为负。
  - `priceBasis` 取值：`local-prices` 表示本机当前价格表（本机统计与桌面对云端的桥接）；`uploaded-prices` 表示云端按各设备上传时的价格表冻结。
- 消费端校验。任一不满足就丢弃整个对象，但保留旧核心字段：
  - 三个金额都是有限数，`readSavedUsd` 与 `writePremiumUsd` 都 ≥ 0；
  - |net − (read − premium)| ≤ 1e-6 × max(1, read + premium)；
  - `cacheSavedUsd` 同时存在时，与 `readSavedUsd` 的差不超过同一容差；
  - 两个兜底计数是整数，不小于 0，也不大于对应的读取量与写入量；
  - `priceBasis` 属于已知取值；
  - 未知附加键可以忽略。
- 输出位置：
  - 本机：主看板与实体看板的 `summary`、`comparison.current/previous.summary`、明细 `filteredSummary`。这些都出自同一个汇总器。
  - 云端：B 期迁移后只保证主看板 `summary`；B3 再扩到其余三类。
- `meta.capabilities.cacheSavings = true` 表示生产者按本节计算。
  - 能力为 true 而对象缺失：该范围不可得。
  - 能力缺失：旧云端。此时桌面可以桥接计算（`priceBasis: local-prices`），Android 显示不可得。
- 共享 fixture 新增两份：
  - `cache-savings-v2.json`：列价的正值、兜底计数、负净值、已知 0。
  - `cache-savings-invalid-v2.json`：拆分不可证明时对象缺失；非法形状整体丢弃而核心保留。
