# 多工位协作约定

适用：维护方同时用多台电脑、多个智能体与多个订阅账号并行开发本仓库时。外部贡献者只需读 [CONTRIBUTING.md](../CONTRIBUTING.md)，本文对你没有额外要求。

核心原则：**GitHub 仓库是唯一的同步通道。** 各工位之间看不到彼此的对话与本机状态，只通过 Issue、PR、评论和仓库里的文档交流；没写进仓库的约定不算数。本仓库是公开的，所以写进 Issue、评论、分支名、提交和 PR 的一切都公开（见第 9 节）。

## 1. 角色

| 角色 | 由谁担任 | 负责 |
|---|---|---|
| 负责人 | 维护者本人 | 拍板 C 级改动与问询、改 GitHub 仓库设置、发版、真机验收签字 |
| 协调者 | 维护方项目里的协调 Claude | 拆任务、开任务 Issue、打 `可开工`、指定共享文件的拥有者与迁移编号、评审、收回超时租约、向负责人汇报 |
| 实现工位 | 云端 Claude 线程、本机智能体（Claude Code、MiniMax、Codex 等） | 领任务、写代码、开 PR、把 PR 推到 CI 全绿 |
| 验收工位 | 带真机的实现工位 | 跑本机全量门禁与真机走查，回填验证状态 |

一个工位可以同时是实现工位和验收工位。协调者也可以领文档类任务，但不评审自己的 PR。

## 2. 工位

工位名 = `智能体@代号`。代号是两位小写字母或数字组成的不透明短码，**不得使用机器名、用户名或任何能定位到人或设备的标识**；代号与真实设备、订阅账号的对应关系只记在各自本机未跟踪的 `~/.config/tokenledger/stations.json` 里。

| 代号 | 系统 | 能做的门禁 | 适合领的任务 |
|---|---|---|---|
| `w1`、`w2` | Windows | Tauri 桌面、WebView2、缩放与 Snap、托盘；有 Android SDK 时含 Android 门禁 | 桌面交互、Windows 专属行为、Android |
| `m1`、`m2` | macOS | macOS 窗口、DMG 打包 | macOS 窗口与打包、跨端复核 |
| 分支短码末两位，如 `v2` | Linux 云容器 | Vite 浏览器走查、Rust 测试、前端测试、文档门禁 | 前端、Rust、契约与文档、CI 修复 |

- 云端 Claude 线程的代号取它分支名 `claude/project-thread-<短码>` 末段的**最后两位**，例如分支 `claude/project-thread-84xjv2` 的工位名是 `claude@v2`。和工位表里已有的代号重复时改取最后三位，并在登记评论里写明。云端没有 Android 模拟器、Supabase 本地栈与签名证书，不领带 `需Android`、`需Supabase` 的任务的验收部分。
- 智能体名用小写：`claude`（含云端线程与本机 Claude Code）、`minimax`、`codex`，新增的按同样方式命名。
- 工位表放在置顶的「工位表」Issue 里，每个工位一条评论：工位名、能力、当前任务、最后心跳。工位登记时自己发这条评论并记下评论 ID。

## 3. 署名

所有工位都经维护者的同一个 GitHub 账号操作，界面上分不出是谁写的，所以：

- 每条 Issue 评论、PR 评论、评审回复、Issue 正文、PR 正文的**第一行可见文字**以 `[工位名]` 开头，例如 `[minimax@w1]`。平台要求放在正文最前面的署名块（例如项目线程的归属块）放在它前面。
- 每个提交信息末尾加一行 `Agent: <工位名>`。squash 合并时把这一行留在合并提交正文里。
- 没有 `[工位名]` 前缀的评论视为维护者本人所写，按负责人的意见处理。
- **订阅账号名、邮箱、额度数字不写进仓库。** 工位换了账号不改工位名；额度用完按第 5.4 节停下。

## 4. 事实源与状态

| 要知道的事 | 去哪看 | 谁写 |
|---|---|---|
| 有哪些任务、谁在做 | `任务` Issue 与标签 | 协调者开 Issue、工位评论认领 |
| 进度 | PR（进度的单位是 PR，不维护共享进度文件） | 实现工位 |
| 工位在线与心跳 | 「工位表」Issue | 各工位只改自己那条 |
| 问题与结论 | `问询` Issue 最新一条带「结论：」的评论 | 工位提问、协调者或负责人答复 |
| 会改变产品事实的结论 | `docs/PROJECT.md`、`docs/REQUIREMENTS.md`、`docs/DESIGN.md`、`docs/contracts/**` | 单写拥有者另开 PR 落盘 |
| 验证状态 | PR 正文「验证」一节与任务 Issue；只缺真机时 Issue 加 `待平台验收` | 实现工位、验收工位 |

冲突时的优先级：AGENTS.md 铁律 > 已答复的问询 > 契约与需求、设计文档 > 任务 Issue > 代码现状。发现冲突就开问询，不要自己选一边悄悄做。

含本机路径、机器标识、截图与完整日志的证据不进本仓库：PR 里只写结论、命令与结果末尾几行、SHA-256；原始材料留在维护方本机或私有归档里。

## 5. 任务生命周期

### 5.1 开任务

协调者把每个任务开成一个 Issue（用「任务」模板），写清范围、验收、会改的共享文件、需要的能力标签与改动级别。依赖都已合并、共享文件不冲突时，协调者打 `可开工`。

### 5.2 认领：先评论，再重读，最早的赢

读标签再加标签不是原子操作，两个工位可能同时领到同一个任务。所以：

1. 只看带 `可开工`、没有 `进行中`、没有 `阻塞` 的 `任务` Issue，并跳过自己没有能力的（例如云端工位跳过 `需Windows`）。
2. 评论 `[工位名] 开工：分支 <分支名>`。
3. 约 1 分钟后重读评论：**时间最早的一条「开工」赢**。赢的加 `进行中`；输的评论 `[工位名] 撤回` 并换下一个任务。
4. 协调者直接派给某个工位的任务，Issue 正文写明工位名，其他工位不领。

### 5.3 分支与 PR

- 本机工位的分支：`<智能体>-<代号>/i<Issue 号>-<简短英文名>`，例如 `minimax-w1/i12-webdav-import`。云端线程沿用平台指定的 `claude/project-thread-<短码>`，任务号写在 PR 正文里。
- 分支推到本仓库，第一次推送就开 draft PR，正文写 `Closes #<任务 Issue 号>`，按 PR 模板填写。
- PR 标题就是 squash 后进 `main` 的提交主题，**必须含中文**（CI 会查），格式同提交主题，例如 `统计：增加上一周期曲线`。
- 一个任务一个 PR；一个 PR 只做一件事。

### 5.4 租约与心跳

- 领取后 3 小时内必须有推送；之后至少每 3 小时推送一次，或更新工位表里的心跳。云端线程的推送本身就算心跳。
- 做不完、额度用完或要停下时，主动去掉 `进行中`，在任务 Issue 评论 `[工位名] 暂停：<原因>，现状见 PR #n`。
- 超过 3 小时没有推送也没有心跳，协调者在 Issue 提醒；再过一轮仍无动静就去掉 `进行中`，任务回到可领状态。
- **更新心跳只能按评论 ID 编辑自己的那一条**。所有工位共用一个 GitHub 账号，「编辑最后一条评论」之类的命令会改到别人的评论，禁止使用。

### 5.5 并行上限

- 每个工位名下未合并的 PR 最多 2 个：1 个在做的 draft，加 1 个已转 ready 等合并的。等合并时可以领下一个任务，不要空等。
- 全仓库同时打开的 B 级 PR 不超过 2 个。云端线程同时在跑的不超过 5 个，以免挤占订阅额度。

### 5.6 不碰别人的分支和 PR

- 不往别的工位的分支推提交，不在别人的 PR 上继续改；评审意见写在评审里由原工位改。
- 要接手：在任务 Issue 评论 `[工位名] 接手申请：<原因>`。原工位、协调者或负责人同意后，原工位去掉 `进行中`；接手方从 `main` 新开自己的分支，在新 PR 里链接原 PR，原 PR 由原工位或协调者关闭。

### 5.7 卡住了

- 评论 `[工位名] 阻塞：<原因>，转做 #m`，去掉 `进行中`、加 `阻塞`，转做别的任务。
- 同一个 CI 失败修了两次仍不过，停下，在 Issue 写失败要点并开问询，不要第三次硬试。
- 命令超过 10 分钟没有输出就中止并如实记录（AGENTS.md「前台有界命令」）。

## 6. 共享文件与冲突

- **单写文件**沿用 AGENTS.md 铁律：`docs/PROJECT.md`、`docs/REQUIREMENTS.md`、`docs/DESIGN.md`、`docs/contracts/**`、Supabase 迁移编号、lockfile（`package-lock.json`、`src-tauri/Cargo.lock`、Android Gradle 锁）与版本文件。任务要改哪一个，由协调者在任务 Issue 里写明唯一拥有者；没写的不能改，需要时在 PR 的「与计划的偏离」里提出。
- 会改同一批共享文件的任务，协调者不同时放出 `可开工`。
- 新的 Supabase 迁移编号由协调者写进任务 Issue，工位不自己取号。
- 加依赖的 PR 同一时间只有一个在开；它合并后，其他分支合并 `main` 再继续。
- PR 与 `main` 冲突时，把 `main` 合并进自己的分支解决，不改写已推送的历史（squash 合并后分支历史本来就不进 `main`）。
- 同一台机器上跑多个智能体时，每个任务一个仓库外的 worktree，开发服务器端口按工位错开（`1420` 起，每个工位加 10），不共享构建输出目录。

## 7. 合并与门禁

| 级别 | 范围 | 合并条件 |
|---|---|---|
| A | 文档、测试、前端界面、不碰下面路径的修复 | CI 全绿 → 自动 squash 合并 |
| B | `docs/contracts/**`、`StatsData` 与跨端统计口径、Supabase 迁移与 RLS/RPC、同步格式（WebDAV）、密钥与本地安全存储、额度来源、`.github/`、发布脚本、新增依赖 | CI 全绿 + 另一个工位或协调者评审，评论 `评审通过` 后合并；PR 加 `B级` 标签 |
| C | 碰 AGENTS.md 铁律或公开仓库红线、版本号与发版、`docs/PROJECT.md` 的架构决策 | 同 B 级，另需负责人在 PR 里批准；PR 加 `C级` 标签 |

- 实现工位在 PR 模板里自评级别，拿不准就往高一级报。写代码的工位不评审自己的 PR。
- **CI 绿是合并门槛，不是验收。** 只缺真机或外部服务的改动合并后在任务 Issue 加 `待平台验收`，由验收工位在本机跑对应全量门禁与走查后回填结果再关闭（AGENTS.md「诚实验收」）。
- 合并方式统一为 squash；合并提交主题即 PR 标题。

## 8. 问询

拿不准时开问询，不要空等：

- 用「问询」模板开 Issue，标签 `问询`，标题 `[问询] 一句话问题`。写清：关联任务、问题、已查过的文档位置、至少两个选项及后果、你的推荐、不答复时的默认做法、是否阻塞。
- **非阻塞就按推荐继续**，PR 里注明；**阻塞就转做别的任务**。碰铁律、契约、迁移、密钥、发版的问题一律算阻塞。
- 协调者答复格式：`结论：…`、`理由：…`、`需要改的文档：…`。需要负责人拍板的加 `待负责人`，答复后加 `已答复` 并关闭。工位以最新一条带「结论：」的评论为准。
- PR 评审里的小问题直接在 PR 评论里问，以 `【问询】` 开头；一来一回说不清就转成问询 Issue。

## 9. 公开仓库红线

Issue、评论、分支名、提交信息、PR 标题与正文、截图都会公开，所以一律不得出现：

- 凭据：令牌、API key、cookie、会话数据、私钥、订阅账号名与邮箱。
- 身份与环境：机器名、本机用户名、本机绝对路径、内部域名与主机名、内网地址。
- 内部过程材料：任务台账、派单简报、证据日志、内部审计（范围见 [内部协作材料](internal-collaboration-materials.md)）。
- 竞品信息：参照或对标的其他产品的名称、仓库、作者，以及“对齐某产品”“参考某产品”之类的表述。提交信息、PR 与 Issue、代码注释、日志输出、文档、分支名、标识符与文件名一律用中性描述（例如“外部用量文件导入”“第三方网关”）。对标分析只留在维护方私有材料里。

推送前用本机未跟踪的发布清洁清单自查；发现已经推上去的，先告诉负责人，不要自己改写历史。每台机器用独立、仅限本仓库的细粒度令牌，便于单独吊销；shell 环境里不放真实的服务商密钥。

## 10. 交接

云端线程随时可能结束，本机会话也会被打断。每个 PR 在转 ready 前、或工位停下前，PR 正文「交接」一节写清：

1. 现在做到哪一步、还差什么；
2. 跑过的验证命令与结果，没跑的和原因；
3. 下一个接手者第一步该做什么。

下一个接手的工位只读 Issue、PR 和本仓库文档就能继续，不依赖上一方的对话上下文。
